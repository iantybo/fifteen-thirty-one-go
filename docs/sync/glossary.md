# Glossary

> Part of the [Optimistic Sync Engine docs](./README.md). See also [reconciliation.md](./reconciliation.md), [action-lifecycle.md](./action-lifecycle.md).

Definitions of the vocabulary used throughout the sync engine docs and code.

### Revision

A per-game integer defined as the **count of durably-recorded moves** for that
game (`gameRevision` in `resync.go`). It is monotonically non-decreasing and
cheap to compute. The client uses it **only for ordering** — comparing newer vs.
stale to reject out-of-order snapshots — and never interprets the absolute
value. A freshly-fetched snapshot starts the client engine at revision 0. See
[api-contract.md](./api-contract.md#revision-semantics).

### Client id

The stable, deterministic identity of a queued action, in the format:

```
c:<gameId>:<userId>:<seq>        e.g. c:42:7:5
```

Generated by `IdGenerator` (`clientId.ts`) with a monotonic `seq` and no
`Math.random()`, so ids are reproducible in tests and stable across retries. The
client id is the identity used everywhere: dedupe, reconciliation, and rollback.
The server echoes it back in the resync response.

### Optimistic state

The `CribbageState` the UI actually renders: the confirmed base snapshot with
every still-`pending`/`inflight` action folded in via the reducer
(`EngineGameState.optimisticState`). It is a *prediction* — never the raw server
snapshot — and it moves the board before the network round-trip completes. The
reducer predicts turn order, the pegging total, and which of *my* cards left my
hand, but **never scores** (see [faq.md](./faq.md#why-doesnt-the-reducer-predict-scores)).

### Confirmed snapshot

The last authoritative `GameSnapshot` received from the server
(`EngineGameState.confirmedSnapshot`). It is the trusted base from which
optimistic state is derived. It is replaced wholesale on each successful
reconcile; the UI never reads it directly.

### Reconcile

The process of pulling optimistic client state back toward authoritative truth
when a fresh snapshot arrives (`SyncEngine.reconcile`). It rejects stale
snapshots, drops confirmed/rejected actions, adopts the new base, re-folds
remaining pending actions on top, and drops any the reducer can no longer apply.
Its outcome is a `ReconcileResult`. See [reconciliation.md](./reconciliation.md).

### Rebase

The special case of reconcile where the server has advanced the game (e.g. the
opponent moved) but the client's outstanding actions still apply. The engine
re-derives optimistic state by replaying those actions **on top of the newer
authoritative base**, in author order, rather than patching the old prediction.
Rebasing is trivial because the reducer is pure and total.

### Fold

Applying a sequence of actions onto a base state, one after another, in author
order, via the reducer (`foldActions(cloneState(base), pending, myPosition)`).
It returns the resulting `state` plus a `skipped` list of actions that could not
be applied to that base. "Fold onto a new base" is the mechanical core of both
the optimistic recompute and the reconcile/rebase step.

### Transient error

A delivery failure that is expected to succeed on retry: network errors, HTTP
5xx, 408 (timeout), and 429 (rate limit). The action stays `pending`, the engine
backs off (`backoffDelayMs`: 0, 250ms, 500ms, 1s, … capped at 15s), and the
flush pass stops so ordering is preserved. Classified by `isPermanentError`
returning `false` in `errors.ts`.

### Permanent error

A delivery failure that will never succeed on retry: HTTP 4xx **except** 408 and
429 (an illegal move, out-of-turn play, or duplicate). The action is marked
`rejected`, removed from the queue, its optimistic effect rolled back, and the
rejection surfaced to the user. Classified by `isPermanentError` returning
`true`. See [action-lifecycle.md](./action-lifecycle.md#transient-vs-permanent).

### Related terms

| Term | Short definition |
| --- | --- |
| `QueuedAction` | A durable queue entry: `clientId`, `action`, `status`, `baseRevision`, `seq`, `attempts`. |
| `QueuedActionStatus` | `pending → inflight → confirmed / rejected`. |
| `SyncAction` | The engine's action vocabulary: `discard`, `play_card`, `go`, `ready_next_hand`. |
| `KeyValueStore` | The injected storage interface backing the queue (localStorage or memory). |
| `EngineDeps` | The injected dependency bag: `now`, `setTimer`, `store`, `makeWs`, `gameApi`. |
| `game_update` | The WebSocket event the server broadcasts as an invalidation signal, prompting a resync. |
